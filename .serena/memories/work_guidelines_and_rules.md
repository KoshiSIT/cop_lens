# 作業ガイドラインとルール

## 🚨 重要: ファイル変更の原則

### **ユーザーの指示がない場合は、絶対にファイルを変更・作成しない**

ユーザーが明示的に「実装してください」「変更してください」「作成してください」と指示するまで、以下を行わない：
- ファイルの変更
- ファイルの作成
- コードの実装

### **理由:**
ユーザーは実装と構造を把握できないまま進むと、正しい指示ができなくなる。

---

## ✅ 推奨される作業フロー

### **1. 提案フェーズ**
```
ユーザーからの要望
  ↓
現状のファイル構造を確認（read_file, list_dir, find_symbol）
  ↓
変更内容を提案（具体的なコードを提示）
  ↓
ユーザーの承認を待つ
```

### **2. 実装フェーズ**
```
ユーザーの承認または「実装してください」の指示
  ↓
実装開始
  ↓
変更内容の要約を提示
```

---

## 📋 作業時のチェックリスト

### **提案時:**
- [ ] 現在のファイル構造を確認した
- [ ] 変更が必要なファイルをリストアップした
- [ ] 各ファイルの変更内容を具体的に説明した
- [ ] ユーザーに承認を求めた

### **実装時:**
- [ ] ユーザーから明示的な指示を受けた
- [ ] 変更するファイルを1つずつ処理
- [ ] 各変更後に何を変更したか説明

### **実装後:**
- [ ] 変更したファイルのリストを提示
- [ ] 各ファイルの変更内容を要約
- [ ] テスト結果を確認

---

## 🎯 具体例

### ❌ 悪い例:
```
ユーザー: 「メソッド検出を実装したい」
AI: 「実装しました！」（勝手に7個のファイルを変更）
```

### ✅ 良い例:
```
ユーザー: 「メソッド検出を実装したい」
AI: 
  1. 現状確認（read_fileで構造を把握）
  2. 変更提案（どのファイルをどう変更するか提示）
  3. 承認待ち「この設計で進めますか？」
  
ユーザー: 「実装してください」
AI: 
  1. ファイルを1つずつ変更
  2. 各変更の説明
  3. 完了後に変更内容を要約
```

## 💡 コミュニケーションのベストプラクティス

### **常に:**
- ファイル構造を確認してから提案
- 変更内容を明確に提示
- ユーザーの承認を待つ
- 変更後は必ず要約

### **避ける:**
- 勝手にファイルを変更
- 複数ファイルを一気に変更
- 説明なしの実装
- ユーザーが把握できないスピードでの作業
